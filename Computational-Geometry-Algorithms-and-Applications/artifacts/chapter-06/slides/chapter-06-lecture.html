Start with the user-facing problem: after a map has been built, a query point should identify its containing face quickly. The subdivision may come from streets, parcels, visibility regions, or any planar embedding. The chapter's theme is the tradeoff between preprocessing space and query time, with trapezoidal maps giving a randomized structure whose expected behavior is small enough to be practical.

Slabs Are Fast But Large

Slab Strategy

Sort all vertices by \(x\). A query first chooses a vertical slab, then locates the interval between stored segments inside that slab.

Storage Blow-Up

Every segment crossing many slabs is copied into many slab lists. Fast queries come with possible quadratic storage.

query: \(O(\log n)\) after large tabulation
Use slabs as the natural first attempt. They make the query logic easy: compare the x-coordinate to find a slab, then compare the point to the ordered segments in that slab. The weakness is not query time but replication. A long segment can appear in many slab lists, so a subdivision with many crossing spans can force much more than linear storage.

Trapezoidal Map

Construction Idea

Place all segments in a bounding box. From every segment endpoint, shoot vertical extensions until they hit another segment or the box.

  • Vertical walls stop locally, not across the entire subdivision.
  • Every cell is bounded by at most two segment pieces and two vertical walls.
  • The refinement supports a search structure built during insertion.
Introduce the trapezoidal map as the local alternative to full slabs. The vertical extensions are only drawn from segment endpoints and they stop at the first obstacle. This keeps the decomposition tied to the input geometry rather than to every global vertex slab, and it prepares the ground for an incremental update rule.

Why Faces Are Trapezoids

Lemma 6.1

With non-crossing segment interiors and no vertical input segments, each cell has at most one top edge and at most one bottom edge.

Orientation Intuition

If two distinct upper boundaries could both appear over the same x-range, a vertical line would see an impossible crossing or an unclosed face boundary.

Phrase Lemma 6.1 geometrically rather than as a memorized fact. A face cannot have two unrelated top chains over the same vertical slice without forcing a crossing or another vertical wall between them. The orientation assumptions, especially no vertical segments and disjoint interiors, make the top-bottom description unambiguous.

Four Records Define One Cell

top

segment immediately above the cell

bottom

segment immediately below the cell

leftp

endpoint that induces the left wall

rightp

endpoint that induces the right wall

cell = \((top,bottom,leftp,rightp)\)
Make the data representation concrete. A trapezoid is not stored as a long boundary cycle; it is stored by four references. The top and bottom are segment records or the bounding box, and the left and right walls are identified by the endpoints that generated them. This compact record is what later leaves can point to.

Linear Complexity

Neighbor Invariant

At most a constant number of trapezoids can have the same defining endpoint as their left wall, distinguished by upper and lower neighbors.

|\(T(S)\)| = O(n)

Why It Matters

The map itself is small enough. The remaining challenge is to keep the associated search structure small in expectation.

Give the linear-complexity proof as a charging argument. Each trapezoid has a left wall, and that wall comes from an endpoint or the bounding box. The local neighbor structure prevents one endpoint from being charged by too many trapezoids. This is the first reassurance that the geometry is not the source of the later superlinear risk.

Search DAG Query Walk

Decision Nodes

x-nodes: compare query \(q_x\) with an endpoint x-coordinate.

y-nodes: test whether \(q\) lies above or below a segment.

Leaves

Each leaf stores one current trapezoid. During insertion, replaced leaves are rewired to a small new decision subgraph.

The search structure is a directed acyclic graph, not necessarily a tree, because later replacements can have several incoming pointers. A query follows comparisons: first x-type decisions against endpoints, then y-type decisions against segments. The invariant is synchronization: every leaf reached by the current decisions names the trapezoid of the current map that contains the query point.

Randomized Incremental Loop

State After \(i\) Insertions

\(T(S_i)\) is the trapezoidal map for inserted segments. \(D\) is the query DAG whose leaves point into that map.

Random Order

The analysis depends on the insertion permutation, not on geometric luck. Expensive events become unlikely backwards.

Describe the algorithm as a maintained pair. The map T of S_i is the geometric subdivision after i inserted segments, and D is the search structure that can locate points in it. Each insertion first finds where the new segment begins, follows the cells it crosses, replaces those cells, and then patches the affected leaves in the DAG.

Follow Segment

Walk Rule

Once the segment enters a trapezoid, leave through the right wall. The next cell is the upper-right or lower-right neighbor according to where the segment crosses the wall.

  • Endpoint location starts the walk.
  • Each crossed trapezoid is recorded in order.
  • The ordered list controls replacement and DAG rewiring.
The follow operation is local. After locating the left endpoint of the segment, the algorithm does not query the DAG again for every crossed cell. It walks through neighbor pointers, deciding at each right wall whether the segment continues through the upper-right or lower-right neighbor. This ordered crossed sequence is exactly the geometry that must be removed and rebuilt.

One-Trapezoid Replacement

Four New Cells

If the new segment lies completely inside one old trapezoid, its endpoints create left and right caps plus upper and lower trapezoids.

Leaf Replacement

The old leaf is replaced by a small decision subgraph: compare to the two endpoints, then compare to the segment.

Treat the one-trapezoid case as the basic patch. The segment starts and ends inside the same old cell, so the old cell disappears and up to four new cells appear: a left cap, a right cap, and the regions above and below the segment. The corresponding old DAG leaf is replaced by a tiny decision structure that distinguishes those four outcomes.

Multi-Trapezoid Replacement

Crossed Sequence

For \(\Delta_0,\Delta_1,\ldots,\Delta_k\), remove all crossed trapezoids and create new cells along the inserted segment.

Merges

Consecutive upper or lower fragments with the same defining boundary can merge, keeping the map compact.

DAG Edges

Every incoming edge to an old crossed leaf is redirected into the replacement subgraph for that old trapezoid.

The general insertion is the same idea repeated along a sequence of crossed trapezoids. The first and last cells handle the endpoints, while the middle cells are split by the segment. Some adjacent new fragments merge when they share the same top or bottom boundary. In the DAG, the important bookkeeping is that every pointer into a removed leaf must now enter the correct local replacement.

Backwards Analysis For Queries

Query Path Bound

For a fixed query point, the probability that insertion \(i\) changes its search path is bounded by the chance that one of a constant number of defining objects was inserted last.

\(P_i \le 4/i,\qquad E[\text{path length}] \le 12H_n\)
Backwards analysis asks what would have to be deleted from the final structure for the query point's containing trapezoid to have looked different one step earlier. Only a constant number of defining objects matter for that trapezoid, so the last inserted relevant object has probability at most a constant over i. Summing those probabilities gives the harmonic bound, often stated here as at most 12 H_n comparisons in expectation.

Expected Size And Build Time

Search DAG Size

Each insertion contributes a replacement graph proportional to the number of crossed trapezoids.

Expected Work

Random insertion makes the expected crossed total and update work \(O(n\log n)\).

expected preprocessing: \(O(n\log n)\)
Separate the two expectations. Query paths are logarithmic in expectation, and the size and construction work are bounded by summing expected replacement costs over insertions. The final guarantee is an expected O(n log n) construction with linear expected map complexity and logarithmic expected query time.

Back To Subdivision Faces

Refinement, Not The Answer

The trapezoidal map refines the original subdivision. A query leaf identifies a trapezoid, then the trapezoid stores a pointer to the original DCEL face.

Application View

The data structure answers the map question even though the internal search passes through auxiliary vertical walls.

Return to the original problem. The data structure does not report an artificial trapezoid as the final semantic answer. Each trapezoid knows which face of the original subdivision it lies inside, typically through a DCEL face pointer. This lets the randomized structure serve point location in the original map.

Degeneracy By Shear

General Position Is A Tool

A symbolic shear can remove vertical segments and equal x-coordinates without changing the combinatorial meaning of the query.

Lexicographic Comparisons

Compare \(x+\varepsilon y\) symbolically. When a query lies on a segment, report the incident face information explicitly.

Degeneracy handling should sound like careful implementation rather than a separate theorem. A tiny symbolic shear lets comparisons behave as though no segment is vertical and no two endpoints share an x-coordinate. The data structure still needs an explicit convention for a query on an input segment: it should report the segment or the incident face information instead of pretending the point is strictly above or below.

Tail Estimate To Worst-Case Query

From Expected To Controlled

The chapter's tail-estimate theme turns the expected query bound into a practical restart rule.

Test-Point Reduction

It is enough to test representative points associated with final trapezoids. If any path is too long, rebuild with a fresh random order.

Close with the reliability message. The randomized construction gives expected logarithmic query paths, but applications may want a worst-case cap for the constructed structure. The tail-estimate argument reduces checking all possible query points to checking representative points for final trapezoids. If the constructed DAG has a path that is too long, the algorithm can restart with a new random permutation and use the successful run as a certificate.
