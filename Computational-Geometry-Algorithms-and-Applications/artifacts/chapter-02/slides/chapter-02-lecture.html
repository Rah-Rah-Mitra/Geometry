From Application Geometry To Closed Segments

Predicate Contract

A point \(p\) lies on closed segment \(\overline{ab}\) when it is collinear with \(a,b\) and its coordinates are between the endpoint coordinates.

Endpoint Contacts

Two segments intersect even if they only share an endpoint. Reporting must avoid treating these as numerical accidents.

closed test: \(p \in \overline{ab}\) vs. open test: \(p \in (a,b)\)
Printed pp. 20-21Segment predicates
Emphasize that the input objects are closed line segments, so endpoints are part of the segment and can be genuine intersections. This is why the predicate must distinguish proper interior crossings from endpoint contacts; otherwise the sweep will miss events or count them inconsistently.

Brute Force Versus Output Sensitivity

Printed pp. 21-22Why output-sensitive algorithms matter
The brute force grid is easy to trust because it tests every pair, but it spends time on pairs that are far apart and never interact. The sparse drawing shows why the target complexity should depend on the number of reported intersections as well as the number of input segments.

A First Sweep Fails: Interval Overlap Is Too Weak

Temptation

Keep every segment whose \(x\)-interval contains the current sweep coordinate.

Failure Mode

A single vertical segment can overlap the \(x\)-intervals of many unrelated segments.

The sweep must maintain vertical order, not just interval membership.
Printed pp. 22-23Design pressure for status tree
Walk through the tempting one-dimensional idea: sweep by x and keep segments whose x-intervals overlap the sweep position. The vertical probe makes the failure visible, because many active segments can share an x-range while being far apart in y, producing too many candidate tests.

Plane Sweep State: Event Queue \(Q\) And Status Tree \(T\)

Event Queue \(Q\)

Stores endpoints and discovered crossings by sweep priority: decreasing \(y\), with a deterministic \(x\)-tie break.

Status Tree \(T\)

Stores the segments intersecting the sweep line in their current vertical order.

Printed pp. 23-24Core data structures
Introduce the two pieces of state slowly. The event queue orders points lexicographically from top to bottom, and the active tree stores the vertical order of segments cut by the sweep line. The entire algorithm is a conversation between these two ordered structures.

Local Adjacency Rule: Only Neighbors Need New Tests

Neighbor Pair

After an event updates \(T\), test the segment immediately above and below the changed block.

Skipped Pair

If another segment lies between two candidates at the sweep line, their crossing cannot be the next local event.

local tests \( \Rightarrow \) queue receives future crossings
Printed pp. 24-25Adjacency economy
The local adjacency rule is the central economy of the sweep. If two segments are separated in the active order by another segment at the current sweep position, they cannot be the next pair to meet below that position. Only neighbors need to be scheduled for future tests.

Lemma 2.1: Interior Crossings Force Adjacency

Visual Proof Idea

Zoom into a small neighborhood of an interior crossing point \(p\).

No Room For A Separator

A third segment between the two crossing segments immediately above \(p\) would have to enter the small neighborhood and create another local event.

Therefore the sweep will eventually test the crossing pair as neighbors.
Printed p. 25Lemma 2.1 visual proof
Present this as a visual proof rather than a formal detour. Just above an interior crossing, the two crossing segments have no other segment between them in sweep order; otherwise that intervening segment would have to pass through the tiny lens around the crossing point.

Clustered Events

When several segments meet at one point, handle them together so the status tree makes one coherent local update.

Printed pp. 25-29Event handling
Explain the three sets attached to an event point. U contains segments starting at the point, L contains segments ending there, and C contains segments passing through from above to below. Clustered events matter because several segments may meet at the same coordinates.

Full Algorithm Dashboard

Loop

Extract the next event from \(Q\), compute its incident sets, report if needed, and update \(T\).

Scheduling

After the local update, test the newly adjacent segment pairs and insert future crossing events.

events \(= 2n + k\) under the no-overlap assumption

Use the dashboard as a rehearsal of the whole sweep. Pop the next event, report the intersection when multiple incident segments meet, update the active order, and then test the new adjacent pairs. The visual separates queue, status tree, and output list so the invariants stay visible.

Correctness Invariant: Everything Above Is Done

Processed Region

All intersections strictly above the current sweep line have been reported.

Frontier

The queue contains every known event that can affect the sweep state below the frontier.

Discovery Mechanism

Any unreported crossing must first appear as a neighbor crossing before the sweep reaches it.

Printed pp. 31-32Correctness
The correctness invariant says that everything strictly above the sweep line has already been handled. Events are processed in priority order, and every future crossing must first become a neighbor crossing that gets inserted into the queue. This turns local tests into global completeness.

Runtime Count: Endpoints Plus Intersections

Queue Events

There are \(2n\) endpoint events and at most \(k\) intersection events to process.

Tree Work

Each event performs a constant number of neighbor searches plus insertions and deletions in \(T\).

Total time: \(O((n+k)\log n)\), with linear output storage.
Printed pp. 32-35Runtime and output size
Connect the running time to counting events. There are two endpoints per segment and one event for each discovered intersection point. Splitting the arrangement into a planar graph supplies the geometric intuition that the output size bounds the extra work caused by crossings.

DCEL Record Model For The Overlay

Vertex

Coordinates and one incident half-edge.

Half-Edge

origin, twin, next, prev, and incident face pointers.

Face

Outer boundary, inner components, and labels.

Printed pp. 35-37Doubly connected edge list
Shift from detecting intersections to representing the subdivided map. The DCEL stores vertices, faces, and directed half-edges with explicit twin, next, previous, origin, and incident-face pointers. The benefit is local navigation around boundaries after the overlay creates many small pieces.

Overlay Updates: Split Half-Edges At Vertices And Crossings

Passing Through A Vertex

Insert a subdivision vertex on the edge and split the two directed half-edges.

Crossing Two Edges

Create the intersection vertex, split both input edges, and rewire local adjacency pointers.

Invariant

Every boundary walk must remain a valid next-pointer cycle after the update.

Printed pp. 37-40Overlay construction
The overlay step is a controlled surgery on the DCEL. When an edge passes through a vertex or two edges cross, the affected half-edges are split and rewired so that the next and previous pointers still trace valid boundary cycles in the refined subdivision.

Face Recovery And Labels From \(S_1, S_2\)

Boundary-Cycle Graph

Follow next pointers to list every directed boundary cycle in the refined subdivision.

Label Propagation

Each output face records the containing face from \(S_1\) and the containing face from \(S_2\).

Holes

Inner cycles belong to the surrounding face rather than becoming independent outer faces.

Printed pp. 40-43Face recovery and labeling
After all splits, faces are recovered by walking boundary cycles. Labels are inherited from the two input subdivisions, so each output face knows which face of S1 and which face of S2 contains it. Holes require special attention because not every boundary cycle is an outer boundary.
