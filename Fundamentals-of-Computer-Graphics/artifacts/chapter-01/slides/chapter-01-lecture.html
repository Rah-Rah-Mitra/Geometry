Open the lecture by making Chapter 1 feel operational rather than ceremonial. The goal is to show that computer graphics is not simply image making, but a chain of representable choices from scene data through programs, APIs, numerical conventions, and finally pixels that can be inspected.

Graphics Is a Network of Jobs

field orientation

Working Definition

Computer graphics studies how programs create, transform, inspect, and display images.

Why Start With Areas?

Each later algorithm belongs to a job: specifying geometry, deciding visibility, encoding color, driving motion, or converting data into a visual explanation.

Instructor Emphasis

  • Applications often combine several areas.
  • Good graphics software keeps those responsibilities inspectable.
  • The field is algorithmic, mathematical, and empirical at once.
Use this slide to replace a simple list of areas with a dependency picture. Ask students to name a familiar graphics application and locate the areas it touches. The important conclusion is that graphics work is not one algorithm but a set of cooperating responsibilities.

Reading Strategy

Treat applications as stress tests for the course vocabulary. A domain tells us which data, pipeline stages, and debugging views must be reliable.

Common Misread

Rendering is not the whole field. A beautiful final image may depend on modeling choices, acquisition, interaction, animation, or analysis that happens upstream.

This is a good place to connect the introductory chapter to student motivations. A game, CT scan, manufacturing model, or chart can all be graphics, but each brings a different mixture of geometry, sampling, image processing, and user feedback. The table is deliberately a routing map, not a rigid taxonomy.

APIs Are Contracts, Not Magic

program boundary

Contract View

The application describes work; the API standardizes requests; the driver and device choose an implementation; the framebuffer exposes evidence.

Portability Tradeoff

  • Integrated toolkits can give one portable surface.
  • Separate graphics and UI layers expose more platform variation.
  • The core concepts still transfer across APIs.

When a program fails, the contract helps localize the question: bad scene state, wrong API state, invalid resource, or unexpected image evidence?

Frame APIs as a practical separation of responsibility. Students often experience APIs as incantations, so emphasize that an API call carries structured data across a boundary. Later debugging becomes easier when they ask which side of the boundary owns the missing or incorrect fact.

The Triangle Pipeline

ordered data flow

A desktop graphics pipeline is fast because it repeats a restricted drawing story extremely well.

Pipeline Habit

Name the representation at every stage: object coordinates, clip coordinates, screen samples, depth, color.

Pressure Point

Triangles dominate because they are simple enough for reliable interpolation and parallel hardware execution.

Use the pipeline as the first invariant of the course. The stages are not just hardware trivia; they provide a checklist for reasoning about failures. If the rendered image is wrong, students can ask which representation first stopped matching the intended scene.

Visibility: Raster Route

sample ownership

Raster Question

For each primitive, which screen samples does it cover, and is its depth nearer than the depth currently stored?

What To Inspect

  • coverage mask
  • barycentric coordinates
  • interpolated depth
  • owner or object ID buffer
Why It Is Fast

The operation is local: many samples can be tested in parallel, and the z-buffer gives a simple rule for overlapping triangles.

The raster slide should make visibility feel like bookkeeping rather than magic. The key move is that each sample owns a current best depth. A triangle can cover a sample and still lose if another triangle has already supplied a nearer depth value.

Visibility: Ray Route

nearest positive hit

Ray Question

For each image sample, which object is first along the ray, with parameter t > 0?

Same Goal, Different Order

  • Rasterization loops over primitives and covered samples.
  • Ray tracing loops over rays and candidate intersections.
  • Both solve visibility by retaining a nearest valid event.
Debug Variable

The current best hit distance often starts at +inf, then decreases when a nearer surface is found.

Contrast this with the previous slide without making ray tracing sound like a separate universe. Both routes solve the same visibility problem but traverse the work differently. Emphasize the sentinel role of positive infinity as a clean starting value for no hit yet.

Homogeneous Bookkeeping

4D coordinates

Why 4D?

Homogeneous coordinates let camera, projection, and perspective operations compose as matrix operations before the final divide.

Inspection Target

If w has the wrong sign or scale, the final screen coordinate can look mysterious even when earlier 3D values looked plausible.

The notebook artifact turns this into an inspector: object vertices become clip coordinates and then normalized device coordinates.

Introduce homogeneous coordinates as bookkeeping with a purpose, not as an arbitrary extra dimension. The delayed divide allows clipping and projection to fit into the same matrix pipeline. Students should learn to inspect w values whenever projected positions look surprising.

This slide should not become a floating point trivia quiz. The chapter point is that numerical edge cases can simplify graphics code when they are deliberately chosen. Emphasize the pairing of sentinel values with assertions, debug colors, and clear interpretation of false comparisons.

Efficiency Starts With Memory

optimization order

Optimization Order

Write the straightforward version, compile with optimization, profile, then improve data layout and bottlenecks that measurements actually identify.

Modern Bias

  • Memory access often dominates operation count.
  • Coherent traversal can beat clever arithmetic.
  • Readable code is easier to test before tuning.
Use the two grid traversals to make a qualitative performance point without pretending to benchmark a real cache. Students should hear that the first optimization is clarity plus measurement. Only after profiling should they start changing data structures or arithmetic patterns.

Level of Detail Is a Visible Budget

interactivity tradeoff

LOD Rule

Geometry farther from the viewer usually occupies fewer pixels, so it can often use fewer primitives without a visible loss.

Level of detail is not a license to degrade everything. It connects rendering cost to the actual screen footprint and to the tolerance of the task.

Test

Measure frame cost and inspect visual error; both must support the simplification.

The source chapter links pipeline speed to triangle count and then to distance from the viewer. Present LOD as a budget decision grounded in visibility. The right simplification is the one that saves work while staying below a visible or task-relevant error threshold.

Program Vocabulary: Small Types, Big Consequences

class design

Early graphics code becomes easier to inspect when the basic objects say what kind of data they carry.

Design Tension

Separate point and vector types catch some geometric mistakes, while a smaller class set can keep early code simpler.

Instructor Prompt

Which bug would the type system prevent, and which bug would still require an image or assertion?

This slide turns class design into a concrete teaching question. The chapter discusses vectors, homogeneous vectors, colors, transforms, and images because those objects appear everywhere later. Ask students to reason about what each type can protect and what must still be tested dynamically.

Precision Is a Tradeoff, Not a Creed

float versus double

Practical Default

Large stored arrays benefit from smaller representations; delicate geometric computation may need extra precision.

What Counts As Evidence?

  • unstable intersections
  • shading discontinuities
  • missed boundary tests
  • measured memory pressure
Debugging Tie-In

A precision choice should leave a trace: tests, assertions, or a visual diagnostic that reveals when the assumption breaks.

Keep this discussion balanced. The source chapter presents different preferences, which is useful because the correct answer depends on the program. Students should understand that memory footprint, locality, geometric robustness, and observable artifacts all contribute to the precision decision.

Scientific Debugging in Graphics

experimental loop

Method

Start from a visible symptom, form a narrow explanation, alter one condition, and compare the image or diagnostic count.

This feels different from stepping through every pixel. It is still disciplined debugging because the hypothesis predicts what should change.

Rule

Keep the useful diagnostic after the bug is fixed. Future failures often need the same window into program state.

This is the chapter's most distinctive practical advice. Explain why traditional step-through debugging becomes awkward when the same code runs for millions of pixels. The scientific loop gives students permission to use images experimentally while still demanding careful hypotheses and comparisons.

Images as Debug Output

coded state

If a variable exists per pixel, per ray, or per primitive, it can often become a diagnostic picture.

Debugging Rule

Prefer diagnostic images that answer a specific question: direction, ownership, cost, invalid range, or missing contribution.

Tie this slide directly to daily graphics practice. A debug image is not a prettier render capture; it is a measurement channel. Encourage students to name the question before choosing the colors, because otherwise diagnostic output becomes decorative rather than explanatory.

Setting a Trap for a Pixel

determinism

When To Use It

If a scientific image narrows the bug to a pixel, ray, triangle, or sample, set a conditional trap at that case.

Trap Ingredients

  • deterministic run
  • fixed random seed
  • single suspect coordinate or primitive ID
  • assertion or breakpoint near the failing state
This slide connects visual debugging back to conventional debuggers. The trick is not to abandon step-through tools but to arrive at them with a precise suspect case. Determinism matters because a conditional breakpoint is only useful when the same computation happens again.

Chapter 1 Habits

recap

1. Name the Area

Decide whether the current problem is about modeling, rendering, animation, imaging, interaction, visualization, or a combination.

2. Track the Representation

At every pipeline stage, identify the data structure being transformed and the invariant that should still hold.

3. Use Numerical Values Deliberately

Infinity, NaN, signed zero, float, and double are design choices that need clear local meanings and tests.

4. Optimize With Evidence

Start from readable code, profile real bottlenecks, and treat memory access as part of the algorithm.

5. Debug With Images

Turn hidden per-pixel or per-primitive state into diagnostic output that answers a concrete question.

6. Preserve Useful Diagnostics

The best debug views become reusable instruments, not temporary hacks that disappear after one bug.

Opening Exercise For Discussion

Given a broken render, design three debug images that would separate bad geometry, bad visibility, and bad shading.

Close by turning the chapter into habits students can use immediately. None of the points requires advanced rendering yet, but each prepares them for later chapters. The discussion exercise should prompt them to design diagnostics before they start changing code blindly.
